# Архитектура и план разработки · У Илем 5.0

## Принцип
Не переносить оболочку 4.0. Переносить только проверенные идеи, требования и отдельную доменную логику после аудита. Все системы 5.0 проектировать вокруг единой модели объектов и событий.

## Слои
1. **Presentation** — интерфейс, панели, окна, управление камерой.
2. **World renderer** — карта, координатная система, 3D-объекты, персонажи, эффекты.
3. **Application** — сценарии пользователя: создать задачу, утвердить закупку, выполнить этап, осмотреть объект.
4. **Domain** — объекты, строительство, задачи, ресурсы, финансы, персонажи, экология, инфраструктура, время.
5. **Persistence** — версия схемы, автосохранение, ручные слоты, экспорт/импорт.
6. **Local services** — Node.js сервер и адаптер Ollama.

## Центральные сущности
- WorldState: версия, время, сезон, погода, настройки.
- WorldObject: id, type, transform/координаты, зона, состояние, интерактивность, связи.
- BuildingProject: objectId, этапы, смета, материалы, исполнитель, статус.
- Task: id, source, objectId?, stageId?, ownerId?, dueAt?, priority, status, dependencies.
- ResourceItem / InventoryMovement: ресурс, единица, количество, склад, движение, источник.
- PurchaseRequest / PurchaseOrder: позиции, цена, поставщик, источник спроса, статус.
- Inspection / Defect: объект, наблюдение, серьёзность, связанная задача/закупка.
- Character: навыки, энергия, график, роли, текущая задача, автономность.
- Plant: вид, координаты, возраст, здоровье, влажность, сезонная стадия.
- UtilityNetwork: электричество, вода, отопление, подключённые объекты.
- SaveSlot: id, дата, schemaVersion, worldState, integrity hash.

## Ключевые правила целостности
- У каждой сущности стабильный ID.
- Задача, календарь, доска, карточка объекта и этапы читают один источник данных.
- Перемещение задачи меняет её планирование, а не создаёт копию.
- Расход/закупка ресурсов атомарны: нельзя выполнить этап при нехватке материалов.
- Финансовая операция и складское движение записываются вместе.
- ИИ формирует предложения/команды по схеме; валидатор проверяет; пользователь подтверждает; только затем команда меняет состояние.
- UI не хранит самостоятельную копию бизнес-данных.
- Каждая команда имеет результат success/error и понятное сообщение.

## Пространственная система карты
- Канонический PNG фиксируется как background/reference asset с контрольной суммой.
- Отдельный calibration manifest хранит размер изображения, bounds игрового мира, точки привязки и координатные преобразования.
- Каждая сущность мира располагается в координатах мира, а не абсолютных CSS-пикселях.
- Обязательная визуальная проверка: совпадение ключевых ориентиров, объектов и береговой линии с каноническим изображением.
- Отдельные 3D-модели и маркеры не должны изменять/перекрашивать сам исходный PNG.

## План этапов
### Этап 0. Аудит и фиксация
- Сопоставить память, чаты, журнал, README и модули 4.0.
- Сформировать реестр требований со статусами approved/conflict/deferred/audit.
- Сверить все игровые модули 4.0: lighting, interiors, ecology, water, production, construction, базовый HTML и сервер.
- Ничего из 4.0 не копировать без проверки и тестов.

### Этап 1. Архитектурный каркас
- Единый проект и запуск.
- Модель данных, ID, события, сохранение.
- Сцена с утверждённой картой и координатами.
- Выбор объектов и карточка выбранного объекта.

### Этап 2. Вертикальный игровой цикл
- Создать задачу из карточки объекта.
- Назначить персонажа и срок.
- Отобразить задачу одновременно на доске и календаре.
- Создать строительный этап, проверить ресурсы, выполнить его.
- Обновить состояние объекта, склад и финансы.
- Сохранить и восстановить после перезапуска.

### Этап 3. Хозяйственные системы
- Осмотры, дефекты, закупки и сводная закупка.
- Склад, финансы, инструменты и производство.
- Вода, электричество, свет, отопление.

### Этап 4. Живой мир
- Персонажи, навыки, энергия и автономные действия.
- Время, сезоны, погода, растения, урожай, уборка снега/листьев.

### Этап 5. Локальный ИИ
- Ollama health-check и выбор/проверка модели.
- Чат с контекстом проекта.
- Предложения задач/планов через валидируемые команды.
- Подтверждение перед изменениями и закупками.

### Этап 6. Полировка и выпуск
- Визуальная проверка всех панелей.
- Полный набор сценарных тестов.
- Чистый ZIP одной папки.
- README, журнал, инструкция запуска и восстановления.

## Definition of Done для каждого этапа
- Функция реализована, а не просто отображена.
- Успешный тест доменной логики.
- Проверен сценарий через UI.
- Сохранение/загрузка проверены, если функция меняет данные.
- Нет новых ошибок консоли.
- Журнал содержит файлы, commit SHA, проверки и ограничения.

## Реестр открытых решений
1. Внутренний редактор планировок: старое утверждение «включить» против более позднего решения 4.0 «убрать». Архитектура может предусмотреть расширение, но UI/механику не реализовывать до разрешения.
2. Вращение камеры: ранее обсуждалось свободное управление, но не считать обязательным без подтверждения точной UX-модели.
3. Точный состав персонажей и их имена: сохранить настраиваемость; проверить список по архивам.
4. Начальные суммы и количество стартовых ресурсов должны быть конфигурируемыми, даже если значения по умолчанию 2 млн + 500 тыс. резерва.
5. Технологии: Three.js + Node локально — рекомендуемая архитектура, окончательно проверить зависимости и возможность офлайн-запуска до фиксации.

## Технологический стек 5.0 · рабочее решение
- Клиент: обычные HTML/CSS и JavaScript ES modules, без тяжёлого frontend-фреймворка.
- 3D: Three.js r180, локально поставляемая библиотека `vendor/three.module.js` + `vendor/three.core.js`; MIT-лицензия приложена. Никаких CDN-запросов при запуске.
- Сервер: Node.js, локальный HTTP-сервер на loopback-интерфейсе; отдаёт статические файлы, сохранения и API адаптера Ollama.
- Запуск: один BAT-файл из каталога проекта; проверка наличия Node.js и понятная ошибка при отсутствии. Для работы игры не требуется интернет.
- Хранение: версионированное состояние игры в браузерном хранилище с экспортом/импортом и резервным сохранением перед миграцией.
- Не использовать CDN как runtime-зависимость, Godot, телефонную сборку или серверный хостинг.

## Неизменные правила проекта
- Карта берётся из закреплённого Dropbox-источника. Пользователя повторно не спрашивать.
- Телефон отложен.
- 4.0 не переписывать и не удалять в рамках разработки 5.0.
- Не плодить версии. Один каталог 5.0, один журнал, один текущий комплект.
- Не выдавать статическую проверку кода за браузерную/игровую проверку.
